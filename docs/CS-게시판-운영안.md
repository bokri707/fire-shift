# 문의 게시판 운영안 (초안)

- 작성: CS부 / 기준일: 2026-11-04
- 대상: 소방 교대달력 앱 설정 화면의 "문의 게시판" (새로 만들 기능)
- 대표 결정(2026-11-04): 사용자 본인에게만 보이는 1:1 문의. 공개 게시판이 아님. 로그인이 없어서 사용자는 "이 폰에서 만든 문의 번호"로만 구분됨.
- 상태: **초안. 대표 승인 전에는 실행하지 않음.** 이 문서는 운영 방법만 정합니다. 앱 코드·서버는 바꾸지 않습니다.

> **맨 위 주의 3가지**
> 1. 사용자에게 가는 답변, 답변 등록, 메일 발송은 **모두 대표 승인 후**에만 합니다.
> 2. 환불, 보상, 개인정보 삭제, 법 문제, 기록 복구는 CS부가 답하지 않고 **팀장에게 바로 넘깁니다.**
> 3. 문의 내용과 문의 번호는 **CS기록, 메일, 구글 리뷰에 옮기지 않습니다.**

---

## 0. 용어 쉽게 보기

- **서버:** 인터넷에 글을 모아 두는 창고. 앱 밖에 있음.
- **문의 번호:** 앱이 처음 만들어 폰에 저장하는 임의의 번호. 이 번호로 "내 문의"를 찾음. 이름이나 전화번호와 연결되어 있지 않음. 그래도 남의 번호를 알면 그 사람의 문의를 볼 수 있으므로 **소모임 코드처럼 비밀로 취급**함.
- **가리기:** 글은 남기되 내용을 "[개인정보 가림]" 같은 문구로 바꾸는 것. 지우는 것과 다름.
- **영업일:** 토요일, 일요일, 공휴일을 뺀 날.

## 1. 처리 흐름 (접수부터 마무리까지)

| 단계 | 하는 일 | 담당 | 결과 상태 |
|---|---|---|---|
| 1. 접수 | 사용자가 앱에서 글을 보내면 서버에 저장됨 | 앱과 서버 (자동) | 접수됨 |
| 2. 분류 | 5종 중 하나를 고르고, 긴급 여부를 표시함. 개인정보가 있으면 가린 뒤 CS부에 넘김 | 팀장 (하루 한 번 확인) | 확인 중 |
| 3. 초안 | 분류별 처리 기준과 답변 초안(이 문서 3장, 기존 CS-답변모음)을 써서 올림 | CS부 | 확인 중 |
| 4. 팀장 검토 | 체크리스트(7장)로 약속·개인정보·사실 여부 확인 | 팀장 | 승인 대기 |
| 5. 대표 승인 | 답변 내용과 발송(등록)을 승인함 | 대표 | 승인 대기 |
| 6. 답변 등록 | 승인된 답변을 그 문의에 올림. 사용자 폰의 "내 문의"에 보임 | 팀장 (서버 작업) | 답변 완료 |
| 7. 마무리 | 상태 확인, CS기록에 날짜와 분류만 적음, 주간 보고에 넣음 | CS부 (기록·보고), 팀장 (상태 닫기) | 완료 / 보류 |

**상태 이름 (보기 쉽게 통일)**
- 접수됨 → 확인 중 → 승인 대기 → 답변 완료
- 보류(대표 결정 필요), 숨김(가림 처리), 삭제(요청에 따라 지움)

**원칙**
- 사용자가 보낸 글을 한 번에 여러 명이 처리하지 않음. 담당은 팀장 한 명.
- 대표 승인 없이 "답변 등록"을 하지 않음.
- 답변을 올린 뒤에는 고치지 않음. 틀렸으면 새 답변으로 정정함 (대표 승인 필요).

## 2. 분류별 처리 기준과 목표 기간

목표 기간은 **1인 운영 기준 제안**입니다. 대표 승인 시간이 포함된 기간이며, 대표가 바꿀 수 있습니다 (8장 결정 1번).
대표 결정(2026-11-04): 오류·고장 2영업일, 사용법 질문 1영업일, 기능 제안 3영업일, 긴급 건은 **즉시 보고**. 사용법 1영업일을 지키려면 점검은 **영업일마다 하루 2번(오전·오후)** 으로 합니다. 개인정보 삭제 처리 기한(7일)은 제안 그대로 쓰기로 함.

**분류 규칙**
- 글 하나에 여러 내용이 있으면 **가장 급한 것**으로 분류함. 예: 기능 제안 + 기록 사라짐 → 긴급.
- 사용자가 고른 분류와 내용이 다르면 **내용으로 다시 분류**함.
- "이런 기능 되나요?"는 사용법이 아니라 **기능 제안**.
- 같은 내용이 3건 이상이면 주간 보고의 "주요 불만·제안"에 올림.

**대표에게 바로 넘기는 경우 (항상)**
- 기록이 사라짐, 복원 실패, 다른 사람 정보가 보임
- 개인정보 삭제 요청, 개인정보가 적힌 글
- 환불, 보상, 법적 문제 (협박, 명예훼손, 신고 등)
- 돈을 내는 기능, 로그인·회원가입, 전화번호 등 새 개인정보를 받는 기능, 다른 직종, 아이폰 앱
- 여러 명이 같은 고장을 말할 때
- 앱이 켜지자마자 꺼질 때 (이전에 있었던 문제)

## 3. 분류별 앱 안 답변 초안

기존 CS-답변모음에 자세한 답변이 있으면 **그 문서의 번호를 참고**하고, 여기에는 앱 안에 올릴 짧은 답변만 씁니다. 답변은 500자 이내. 모든 초안은 대표 승인 전 발송 금지.

### 3-1. 오류·고장
> 보내 주신 내용 확인했습니다. 불편을 드려 죄송합니다.
> 먼저 인터넷 연결을 확인하신 뒤, 앱을 완전히 껐다가 다시 열어 주세요.
> 같은 문제가 계속되면 어떤 화면에서 어떤 행동을 했을 때 생겼는지 이 문의에 다시 적어 주세요.
> 앱을 지우기 전에는 설정 탭의 백업 기능으로 기록을 먼저 보관해 주세요.

(폰 기종, 안드로이드 버전, 증상 캡처 요청은 CS-답변모음 초안 2 참조. 캡처는 개인정보를 가려서 받기.)

### 3-2. 기능 제안
> 좋은 의견 보내 주셔서 감사합니다.
> 소중한 의견으로 기록해 두었습니다.
> 아직 정해진 계획이 없어서 언제 되는지, 되는지 여부도 지금은 말씀드리기 어렵습니다. 양해 부탁드립니다.

(CS-답변모음 초안 3 참조. "넣겠다", "곧 된다"는 쓰지 않음.)

### 3-3. 사용법 질문
> 문의해 주셔서 감사합니다.
> [상황에 맞는 설정 순서 1~3줄. 예: "설정 탭에서 근무 형태를 고르시면 달력에 근무가 채워집니다."]
> 그래도 달라지지 않으면, 어느 화면에서 막히셨는지 다시 적어 주세요.

(CS-답변모음 초안 1 참조. 달력 근무는 참고용이며 실제 근무는 공식 근무표가 우선이라는 말을 빼지 않음.)

### 3-4. 개인정보·삭제 요청 (긴급, 팀장·대표 승인 후 발송)
> 삭제 요청 잘 받았습니다.
> 개인정보는 신중하게 확인한 뒤 처리하겠습니다.
> 확인을 위해 추가로 여쭤볼 수 있습니다. 처리가 끝나면 이 문의 답변으로 알려 드리겠습니다.

(절차는 4장, 기존 초안 4 참조. 처리 기한은 대표가 정할 때까지 적지 않음.)

### 3-5. 기록이 사라짐·다른 사람 정보가 보임 (긴급, 팀장 승인 후 발송)
> 소중한 내용 보내 주셔서 감사합니다. 담당자가 직접 확인하겠습니다.

## 4. 개인정보가 섞인 글 처리법

### 4-1. 기본 원칙
1. 글에 이름, 별명, 전화번호, 주소, 소모임 코드, 문의 번호, 사진 속 신원 정보가 있으면 **개인정보 글**입니다.
2. CS부는 개인정보를 **옮기거나 저장하지 않습니다.** CS기록에는 날짜와 분류만 씁니다. 답변모음, 메일, 리뷰, 주간 보고에도 넣지 않습니다.
3. CS부에 글을 넘길 때는 팀장이 **개인정보를 가린 뒤** 보냅니다. 예: 이름 → "○○", 전화번호 → "***".
4. 개인정보가 든 글은 팀장이 서버에서 **가리기** 처리합니다 (본문을 "[개인정보 가림]"으로 바꿈). 이것은 서버를 바꾸는 일이므로 **대표 승인 후** 합니다.
5. 답변에는 "개인정보가 들어 있어 가렸습니다"처럼 **사실만** 짧게 적습니다. 가린 내용을 다시 적지 않습니다.
6. 사용자에게 "개인정보를 적지 마세요"라고 안내하되, 비난하는 말투는 쓰지 않습니다.

### 4-2. 삭제 요청이 왔을 때 무엇을 지우는지

| 요청 내용 | 무엇을 지우나 | 누가 | 승인 |
|---|---|---|---|
| 내가 보낸 문의 글을 지워 달라 | 서버의 그 문의 글과 답변 | 팀장 | 대표 |
| 답변에 개인정보가 들어 있다 | 그 답변의 해당 부분 또는 답변 전체 | 팀장 | 대표 |
| 내 폰의 문의 목록을 지워 달라 | 폰의 "내 문의" 목록 (본인이 앱에서 하거나, 개발부 기능 필요) | 본인 | 없음 |
| 폰 기록을 모두 지워 달라 | 폰 기록 초기화. **문의 글은 서버에 남음** → 글 삭제를 먼저 요청하게 안내 | 본인 (설정 > 데이터 > 모든 기록 초기화) | 없음 |
| 소모임 정보를 지워 달라 | 소모임 "이 소모임에서 나가기" (CS-답변모음 3장 참조) | 본인 | 없음 (서버 직접 작업이면 대표) |
| 앱을 지워서 앱 안에서 할 수 없다 | 메일로 요청받아 서버에서 찾아 지움 | 팀장 | 대표 |

**중요**
- "모든 기록 초기화"를 먼저 누르면 **문의 번호가 사라져서 내 문의 글을 찾기 어려워집니다.** 그래서 **글 삭제를 먼저** 요청하도록 안내합니다.
- 삭제 요청자가 본인인지 확실하지 않으면 처리 범위를 좁게 잡고, 판단은 팀장과 대표가 합니다.
- 문의 번호를 요청자에게 **묻지 않습니다.** 번호는 메일이나 답변에 적지 않습니다. 대신 **접수 날짜와 시각, 분류, 짧은 내용**으로 찾습니다. 찾을 수 없으면 팀장이 판단합니다.
- 메일로 온 요청 원본은 그대로 보관합니다. 날짜와 종류만 CS기록에 적습니다.

### 4-3. 삭제 처리 순서
1. 요청 접수 (당일): 원본 보관 → 팀장 보고.
2. 대상 확인: 요청자가 맞는지, 같은 소모임의 다른 사람 기록이 섞이지 않는지 확인.
3. 대표 승인: 무엇을 지울지 정함.
4. 백업 여부 결정: 전역 규칙상 삭제 전 백업이 원칙이지만, 백업본도 개인정보이므로 **백업을 둘지, 어디에 둘지, 언제 지울지는 대표가 정합니다.** (8장 결정 4번)
5. 서버 작업: 팀장이 처리. 처리 후 지워졌는지 한 번 더 확인하고 기록 (날짜만).
6. 답변: 초안 4 (CS-답변모음) 참조. 무엇을 지웠는지 구분해서 적음 (폰 기록 / 서버 글 / 답변). 남는 것도 알려 줌.
7. CS기록: 날짜와 종류만 적음.
- 처리 기한: 방침에 정해져 있지 않음. **제안: 접수 후 7일 안에 처리** (대표 확인 필요).

## 7. 악의적 글 (욕설, 광고, 스팸) 처리 기준

| 종류 | 예 | 처리 | 답변 |
|---|---|---|---|
| 욕설·비방 (내용은 있음) | 욕설만 있는 글, 특정 사람 비난 | 팀장 승인 후 **가리기**. 기능 제안 등 내용이 있으면 나머지는 정상 처리 | 없음 (두 번째부터 짧은 안내 가능. 대표 승인) |
| 광고·홍보·링크 | 다른 앱, 판매, 도박·성인 사이트 링크 | **숨김** (대표 승인 후) | 없음 |
| 스팸·도배 | 같은 글 반복, 하루 3건 제한을 피하려는 반복 | 숨김. 반복이 계속되면 팀장이 개발부에 제한 방법을 요청 (대표 결정) | 없음 |
| 테스트·의미 없는 글 | "ㅁㄴㅇㄹ", "테스트" | 기록만 하고 답 없음 | 없음 |
| 협박·성적 내용·불법 행위 | 특정인 신상 공개, 음란물, 위협 | **즉시 팀장 보고.** 글과 시각을 그대로 보관하고 직접 답하지 않음 | 팀장·대표 결정 (법 문제) |
| 특정인의 개인정보 노출 | 다른 소방관의 실명·번호 공개 | 4장 절차. 즉시 가리기 (대표 승인) | 보통 답하지 않음 |

**원칙**
- 악의적 글에는 **사용자를 비난하는 답을 쓰지 않습니다.**
- 악의적 글이라도 기록은 남깁니다 (날짜·분류만).
- "가리기"와 "삭제"를 구분합니다. 증거가 필요할 수 있는 협박·불법 글은 지우지 말고 팀장에게 먼저 보고합니다.
- 차단(이 폰에서 글을 못 보내게 하는 것)은 번호를 바꿔 우회할 수 있어 효과가 적습니다. 도입 여부는 대표가 정합니다.

## 8. 대표가 먼저 정할 것 (결정 사항)

이 항목들이 정해져야 개발과 운영을 시작할 수 있습니다.

1. **목표 기간 확정**: 2장의 목표 기간과 점검 요일(월·수·금)을 쓸지. 긴급을 누가 몇 시간 안에 볼지.
2. **글을 누가, 어떻게 보나**: (가) 팀장이 서버 편집 화면에서 직접 보기 (추가 개발 없음, 대신 서버 작업이 손으로 이뤄짐) / (나) 앱의 관리 화면을 새로 만들기 (개발 필요, 실수 줄임). 답변을 올리는 방식도 여기에 따라 정함.
3. **서버 변경은 대표 승인 대상**: 새 문의 표 추가, 답변 칸 추가, 가리기 기능, 문의 번호로 읽기 권한 설정. 표를 만들 때는 모든 표에 RLS(보안 잠금)를 켜고, 작업 뒤 Supabase 보안 점검을 돌려 결과를 보고합니다.
4. **삭제 백업 정책**: 삭제 전 백업을 둘지, 보관 기간을 얼마로 할지.
5. **사용자 편의**: 보내기 실패 시 글 유지, 사용자가 자기 글을 폰에서 지우는 버튼, 답변이 오면 알림을 줄지 (알림은 서버 호출 방식을 따져야 함. 비용 점검 필요).
6. **문구 확정**: 5장의 "다른 사람에게 보이지 않는다"는 약속은 **이 기능의 실제 동작이 확인된 뒤에만** 씀. 번호를 아는 사람이 읽을 수 있는 구조라면 이 문구는 넣지 않음.
7. **문서 고치기 (출시 전, 대표 승인)**:
   - `docs/개인정보처리방침.md`: "문의 글과 답변"을 보관 항목에 추가하고, 보관 기간·삭제 방법·문의 번호 설명을 넣음. 현재 방침에는 문의 글 항목이 없음.
   - 구글 플레이 "데이터 보안" 설문: 문의 내용(텍스트) 수집 항목 추가.
   - 구글 플레이 정책 확인: 사용자가 쓴 글이 다른 사람에게 보이면 "사용자 생성 콘텐츠" 규정 대상이 될 수 있음. 1:1 비공개라 대상이 아닐 수도 있어 **확인 필요**.
   - `docs/CS-답변모음.md` 0항(앱이 하는 일)과 5-3항(문의 링크 없음)을 새 기능에 맞게 고치기.
   - 이용약관에 문의 글 보관과 삭제에 대한 문장 추가 검토.

## 11. 확인 필요 (사실 확인이 안 된 것)

1. 문의 글을 서버에 저장하는 방식(표, 함수, 보안 설정)은 아직 정해지지 않았습니다. 개발부 작업 설계를 보고 다시 확인해야 합니다.
2. "내 문의" 목록을 앱이 언제 새로 받아오는지 (앱을 열 때 / 새로고침 버튼 / 설정 화면 진입 시)는 개발 설계 확인이 필요합니다.

5. 답변 목표 기간은 1인 운영 기준 제안이며, 실제 처리 시간을 한두 달 기록한 뒤 조정하는 것이 좋습니다.
